# 水滴观测站 · Agent 团队部署指南

**版本**：v1.0
**日期**：2026-09-27
**定位**：回答一个具体问题——**《多Agent分工方案》里的六个角色，怎么在这个项目里真正跑起来**。分工方案管"谁干什么"，本文件管"怎么启动、怎么协作、怎么收队"。

---

## 一、部署形态：三档，按需升级

| 档位 | 形态 | 适用 | 说明 |
|---|---|---|---|
| **档1 · 角色扮演（现已在用）** | 小迪在同一会话里按工序换角色执行 | 001–005 单篇节奏 | 成本最低。**隔离靠自觉**：每换角色重新只读该角色的定义文件，质检前不回看写作过程 |
| **档2 · 自定义子代理** | 用 Agent 工具派生子代理，指定 `subagent_type` 为本项目 `.codebuddy/agents/` 里的角色 | 单篇流水线中并行度要求不高的环节 | **角色定义文件已就位**（见下节），一次派生一个，干完即收，天然上下文隔离 |
| **档3 · 常驻团队** | TeamCreate 建团队 + 多个角色同时在线，共享任务列表 | 周报（采集日跑）+ 实测系列并行 + 日更压力 | 006 之后按需切 |

**建议路径**：001–005 档1/档2 混跑把接口跑顺 → 006 起按内容量决定是否上档3。和 GUI 实测的"先通再快"是同一条纪律。

## 二、角色定义资产（已入库）

项目目录 `.codebuddy/agents/` 下六个角色定义文件，每个 = 角色的"出厂设置"（职责边界 + 硬纪律 + 产出标准）：

| 文件 | 角色 | 核心约束（一句话版） |
|---|---|---|
| `dropseer-collector.md` | 采集员 | 无来源不入库，脱敏当场做，只交素材不写观点 |
| `dropseer-writer.md` | 写手 | 只用素材包证据，不上网补信息，论点后留注入位 |
| `dropseer-editor.md` | 编辑 | 站长注入一字不丢，不新增实质内容 |
| `dropseer-qc.md` | 质检员 | 与写手不同上下文，只判不改，逐项打勾 |
| `dropseer-artist.md` | 美术 | 质检未过不接稿，AI 图只做氛围，凭证最小授权 |
| `dropseer-ops.md` | 运营 | 数据只记录不美化，不做增长建议 |

**这些文件就是隔离机制的载体**：质检员被派生时只加载 `dropseer-qc.md` 和质检标准，看不到写手的会话历史——"新眼睛"由派生机制保证，不靠自觉。

角色纪律修订走 Git：改定义文件 = 改制度，有版本记录。

## 三、档2 操作流程（单篇，推荐现在就用）

以 001 为例，主编（小迪）操作序列：

```
1. [主编] 收站长指令 → 建任务（TaskCreate：素材/初稿/编辑/质检/配图/推送）
2. [主编] Agent 派生 dropseer-collector，交代选题 → 交回素材包
   ↓ 验收：来源齐全、脱敏完成（接口契约见《多Agent分工方案》§四）
3. [主编] Agent 派生 dropseer-writer，只给素材包+基准文件路径 → 交回初稿
4. [站长] 注入思想（人节点，不可跳）
5. [主编] Agent 派生 dropseer-editor 合并注入 → 发布版草稿（内容冻结）
6. [主编] Agent 派生 dropseer-qc，只给草稿+SOP → 质检报告
   ↓ 不过：回 2 或 5；过：进 7
7. [主编] Agent 派生 dropseer-artist → 配图 + 排版预览
8. [站长] 手机终审（人节点）→ 美术推草稿箱
9. [站长] 点发布（人节点，永远手动）
10.[主编] 48h 后派生 dropseer-ops 复盘（前期小迪兼任即可）
```

要点：**每步派生都是新上下文**，交接物落盘在项目目录（素材包/初稿/草稿/质检报告都是文件），不依赖对话记忆传递——工序之间靠**文件**说话，这就是接口契约的落地形态。

## 四、档3 操作流程（常驻团队）

```
1. TeamCreate team_name="dropseer" （小迪 = team lead / 主编）
2. Agent 派生各角色并 team_name="dropseer" 加入：
   - collector / writer / editor / qc / artist / ops（按当前内容量决定常驻几个）
3. TaskCreate 建任务清单（团队共享任务列表），TaskUpdate 指派 owner
4. 各角色做完在自己任务上标完成，主编检查任务列表推进
5. 需要站长输入的节点（注思想/终审/发布），主编暂停流水线等老板
6. 一期做完：SendMessage 发 shutdown_request 收队 → TeamDelete 清理
```

**档3 的适用信号**（满足其一再切）：
- 周报需要每日采集，但当天还有主线稿在写（两条线并行）
- GUI 实测系列：采集员盯 Release + 写手赶稿 + 美术排版三线并行
- 周更变双更，档2 的串行等待开始拖节奏

**档3 的代价**：并行 = 协调开销。主编要处理消息队列、任务冲突；角色越多，"谁在等谁"越复杂。单人号不值得为架构而架构。

## 五、升级触发器（写死的切换条件）

- **档1 → 档2**：001 定稿发布即切（第一篇完整走一遍档2，验证六个角色定义文件的可用性，实战修订后升 v1.1）
- **档2 → 档3**：出现"两个内容线需要在同一周并行推进"的第一次，即切
- **角色定义修订**：任何角色在实战中被发现纪律缺口 → 改 `.codebuddy/agents/` 对应文件 + git commit，团队里所有后续派生自动用新版

## 六、风险与保险

| 风险 | 保险 |
|---|---|
| 多 Agent 并行写同一文件冲突 | 交接物按目录分区（素材归 04、稿归 03、数据归 05），各角色只写自己的区 |
| 质检员被写手"说服" | 制度上不同上下文 + 定义文件里写明"只对标准负责"；主编发现质检偏软即重新派生 |
| 角色定义漂移（越写越像一个人） | 定义文件进 Git，修订必须 commit；主编定期 diff 角色产出是否符合各自纪律 |
| 凭证泄漏 | 只有 artist 定义文件提到凭证流程，且明令不落盘不复述 |
| 团队资源泄漏 | 档3 收队必须 shutdown + TeamDelete；会话异常结束会自动清理 |

## 七、和既有文件的关系

- 《多Agent分工方案》= 组织架构图（角色/隔离/契约）
- 本文件 = 部署手册（怎么启动）
- `.codebuddy/agents/*.md` = 角色制度本身（每个成员的岗位说明书）
- 《内容生产SOP》v1.1 = 工序手册（干什么）
- 四者配套使用，修订时同步
