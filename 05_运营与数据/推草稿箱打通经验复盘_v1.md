## 一、打通了什么（结论先行）

```
Markdown 稿件
   │  wenyan render  →  带内联样式的 HTML（微信编辑器可直接粘贴，备用路径）
   │  wenyan publish →  渲染 + 图片自动传微信图床 + 建草稿
   ▼
公众号草稿箱（Media ID 返回）→ 手机端人工确认 → 点发布
```

**已实测通过的四道门（任何一道不过就推不进去）**：

| 门槛 | 内容 | 本次结果 |
|---|---|---|
| ① 凭证 | AppID + AppSecret（开发者平台启用，只显示一次） | ✅ |
| ② 网络来源 | 调用方公网 IP 必须进后台 **IP 白名单** | ✅ 加了 `36.163.154.184` |
| ③ 接口权限 | 账号是否有草稿箱接口权限 | ✅ **实测可用**（见 §三） |
| ④ 图片 | 封面/正文图自动传微信图床（需素材接口） | ✅ |

**发布永远人工**：推的是草稿箱，手机端点发布这一下不自动化（合规红线，也是账号保险丝）。

## 二、踩过的坑（六个，都写进了操作手册）

| # | 现象 | 真实原因 | 解法 |
|---|---|---|---|
| 1 | `wenyan --env-file <路径>` 三种写法全报"未提供 AppID" | 该参数实测不生效（不是路径写法问题） | 改用**环境变量** `WECHAT_APP_ID` / `WECHAT_APP_SECRET` |
| 2 | `--app-id wx...` 报"未能找到 AppID 为 … 的凭据" | 该参数只用于**挑选已存好的凭据**，不能首次传参 | 先存凭据（环境变量或 `credential -s`） |
| 3 | 推送报 `40001 invalid credential, access_token is invalid or not latest` | **微信同一时刻只保留一个有效 access_token**：我的自检脚本取了一次，把推送工具缓存的那个顶掉了 | 删 `%APPDATA%/wenyan-md/token.json` 重新获取；已让自检脚本收尾自动清该缓存 |
| 4 | `40164 invalid ip … not in whitelist` | 家庭/办公宽带是**动态公网 IP**，且白名单区块要先启用 AppSecret 才可填 | 把报错里回显的 IP 加进白名单；白名单支持多个 IP，常用出口都加上 |
| 5 | `-c 自定义主题`后正文全裸（无样式） | `-c` 是**替代**内置主题，不是叠加；且 wenyan 内联器**不处理根元素 section** | 主题 CSS 必须把每个元素（p/h1/h2/th/td/pre/img…）写全，字号行高逐块给 |
| 6 | 封面在手机上发糊 | 官方推荐 900×383，但手机端封面被拉伸到约 1080 物理像素，再经微信二次压缩；黑底 + 细银线这种高对比细线最怕压缩 | 用同一套制图函数**按 1800×767 重新渲染**（矢量重绘，非位图放大） |

> 另有两个环境级小坑：sandbox 的 safe-delete 拒绝 `rm` 绝对路径（改用 `node -e fs.rmSync` 可行）；Git Bash 的 `/tmp` 与 Windows Python 眼中的 `/tmp` 不是同一个目录（脚本里别混用）。

## 三、最值得记的一条：**官方口径与实测不一致，以实测为准**

动手前我查了官方文档与开放社区，两条口径说得很硬：

1. "**未完成微信认证的公众号不支持跳转其他网址**" → 菜单只能用公众号体系内链接（这条对，菜单设计已据此调整）；
2. "**草稿箱接口（`draft/add`）适用范围：仅认证**" → 未认证账号调用会返回 `48001 api unauthorized`，社区专员也明确回复"需要已认证的公众号"。

**实测结果：第 2 条对本号不成立。** 本号是**个人主体未认证订阅号**，但 `draft/count` 正常返回、`draft/add` 建草稿成功、`draft/delete` 删除成功。

这件事对本站的意义，比"省了手工复制"大得多——**它本身就是一次标准的"观测"**：

> 文档写的是"应该如此"，实跑出来的是"其实如此"。两者不一致时，只有跑过的人知道真相。
> 这正是「黑盒之外的观测者」这个号存在的理由。

**顺带一个可复用的手法**：验证接口权限，要用**只读接口**去探（本号用 `draft/count`），不要拿"能不能建草稿"去试——既不用清理垃圾，也不污染对方系统。这是测试工程里"先只读探测、再写操作"的老规矩，用在这里同样成立。

## 四、方法论沉淀（可迁移到任何自动化链路）

1. **凭证与代码分离**：凭据只进 `.env.secret`（`.gitignore` 排除 `*.secret`），任何 `.md`、任何提交里都不出现；截图、聊天记录里也不出现。AppSecret 一旦外泄立刻重置。
2. **把"能不能用"做成一条命令**：`check_wechat_ready.sh` 一条命令报出四个门槛的状态，并把错误码翻译成"下一步做什么"。环境会变（IP、token、权限），**自检比记忆可靠**。
3. **永远准备降级路径**：API 是快路，`render` + 手动粘贴是慢路。**慢路必须在动手前就验证可行**，这样 API 走不通时不会卡住整个发布流程（本次慢路先跑通，才敢去试 API）。
4. **口径存疑先小成本验证**：官方说"不行"的事，试一次的成本可能只有五分钟，但结论要自己拿到手。
5. **验证要留下可复现记录**：每一步的原始返回（错误码、Media ID）都落进手册——下次遇到同样报错，不必重新推理。
